# Personal Assistant Agent Requirements

Date: 2026-06-06

## 背景

用户是自由职业者，在家办公后工作和生活边界混在一起，作息不固定，工作时长和任务推进不稳定。用户希望构建一个后续可扩展的个人智能助手，先从飞书接入和简单任务管理开始，帮助自己恢复日常节奏、减少无序感，并逐步形成可持续的工作与休息边界。

这个助手的第一版不追求复杂项目管理，也不追求全自动长期规划。核心价值是：在正确的时间主动提醒用户进入工作、休息、复盘和睡眠状态，并根据用户反馈动态维护当天和后续任务。

## 第一版目标

- 通过飞书与用户交互，优先采用飞书私聊。
- 主动提醒用户该工作、该休息、该睡觉。
- 知道用户今天要做什么，并能在开始工作前告诉用户今日安排。
- 支持用户用自然语言添加、调整、完成、推迟或取消任务。
- 晚上主动询问用户今天做了什么，并据此更新任务列表。
- 记录每次晚间复盘，形成可回看、可用于后续智能分析的历史。
- 在没有任务安排时，主动询问用户是否需要安排今天或明天的任务。
- 提醒语言可以鼓励、俏皮，并支持未来调整风格。
- 整体体验应像个人助手，而不是固定文案闹钟。

第一版按单用户助手实现，只服务用户本人。但数据结构和服务层需要保留 `user_id`，避免后续扩展多人或多渠道身份绑定时重做数据模型。

## 非目标

- 第一版不做复杂项目管理系统。
- 第一版不需要网页或独立 App。
- 第一版不要求自动判断用户是否真的在工作。
- 第一版不做详细时间统计、番茄钟报表或绩效分析。
- 第一版不在休息时间主动打扰用户，除非用户主动安排了额外提醒。

## 默认日程

默认工作日节奏如下：

```text
09:00 开始工作
12:00-13:30 午休，免打扰
13:30 下午工作
18:00 结束工作，进入休息免打扰
23:00 晚间复盘
23:30 睡觉准备提醒
24:00 睡觉提醒
```

休息时间规则：

- 午休期间默认不主动打扰用户。
- 18:00 工作结束后，到 23:00 复盘前默认不主动打扰用户。
- 用户可以在免打扰期间主动找助手。
- 用户也可以主动安排某个休息时间内的临时提醒。

## 提醒行为

工作、复盘、睡觉等计划事件不在开始时刻才提醒，而是在开始前随机提醒。

默认规则：

- 提前 10-30 分钟随机发送提醒。
- 提醒发出后进入等待确认状态。
- 用户确认后停止提醒。
- 如果用户没有反馈，每 10 分钟重复提醒一次。
- 最多重复 3 次。
- 如果 3 次后仍未回应，停止打扰，并在晚间复盘时询问原因。

用户可以回复：

- “知道了 / 收到 / ok”：接受安排，停止当前提醒。
- “推迟 20 分钟 / 半小时后提醒我”：调整下一次提醒时间。
- “今天不做了 / 取消”：更新任务状态。
- “改到明天 / 推迟”：将任务标记为推迟，并重新安排。
- “我现在在做 X”：更新当前状态或任务进度。
- “做完了”：将对应任务标记为已完成。

提醒消息第一版使用“文本内容 + 飞书交互卡片按钮”的组合：

- 消息主体保持像聊天一样自然。
- 卡片按钮提供低成本操作，例如“知道了”“推迟 10 分钟”“推迟 30 分钟”“今天不做了”。
- 用户仍然可以直接输入自然语言回复，按钮不是唯一入口。
- 卡片按钮点击和自然语言回复都应进入同一套任务/提醒处理逻辑。
- 按钮动作应使用渠道无关的内部 action，例如 `ack_reminder`、`snooze_reminder`、`skip_today`，再由飞书 adapter 映射为具体卡片交互。

## 消息格式

第一版需要统一所有飞书回复和提醒的信息格式。应用内应有独立的消息渲染层，避免不同业务模块各自拼接飞书消息。

格式原则：

- 优先使用飞书交互卡片或富文本能力呈现结构化内容。
- 如果飞书对应消息类型支持 markdown 风格渲染，则用统一的 markdown 子集表达标题、列表、强调和任务状态。
- 不依赖飞书不稳定或不通用的 markdown 扩展。
- 所有消息都应有纯文本降级内容，便于调试和后续切换渠道。
- 工作提醒、休息提醒、复盘、任务列表、错误提示分别使用固定模板结构，但模板中的自然语言内容可以由 LLM 生成或润色。
- 内部消息结构应先表达渠道无关的语义，例如标题、正文、字段、操作按钮、重要程度和关联任务，再由具体渠道 adapter 渲染成飞书卡片、富文本或纯文本。

任务列表建议格式：

```text
今天安排

1. [高][工作][未开始] 客户报价 - 09:00
2. [中][工作][进行中] 修改方案 - 13:30
```

提醒建议格式：

```text
准备开始：客户报价

计划时间：09:00
重要程度：高

差不多该切到工作模式了。先打开文件，不用等状态完美。
```

## 任务模型

第一版数据存储使用 SQLite。它足够简单，便于本地开发和部署，同时可以支持任务、提醒、复盘、对话摘要等结构化记录。后续如果需要多设备、多用户或云端部署，可以再迁移到服务端数据库。

任务状态：

- 未开始
- 进行中
- 已完成
- 推迟
- 取消

任务属性：

- 用户 ID
- 标题
- 描述
- 重要程度：高 / 中 / 低
- 任务类型：工作 / 生活 / 休息 / 睡眠 / 复盘 / 临时提醒
- 计划日期
- 计划开始时间
- 预计耗时
- 实际完成时间
- 状态
- 提醒窗口，默认提前 10-30 分钟
- 是否需要确认
- 来源：用户主动添加 / 晚间复盘生成 / 未完成顺延
- 备注

第一版必须支持的属性：

- 用户 ID
- 标题
- 重要程度
- 任务类型
- 计划日期
- 计划开始时间
- 状态
- 提醒确认状态

其他属性可以先支持但不强制填写。

## 任务输入

用户可以自然语言告诉助手任务安排，例如：

```text
明天上午做一下客户报价，比较重要，9 点开始，大概 2 小时。
```

助手应理解并整理为任务：

```text
标题：客户报价
重要程度：高
任务类型：工作
计划日期：明天
计划开始时间：09:00
预计耗时：2 小时
状态：未开始
```

如果用户没有提供足够信息，助手可以用简短问题补全关键字段，但不要让添加任务变得繁琐。

## 无任务状态

如果明天没有任务，助手应在晚间复盘或睡前阶段主动询问：

```text
明天有什么安排吗？
```

如果早上仍然没有任务，助手应在工作开始前询问：

```text
今天还没有安排，要不要先定 1-3 件事？
```

如果用户一直没有给任务，助手不应强行编造任务。它可以提醒用户进入工作时段，并建议先定一个最小起步任务。

## 晚间复盘

晚间复盘默认在 23:00 进行。

复盘目标是轻量更新任务，而不是写日报。默认问题：

```text
今天完成了什么？
还有什么没完成？
明天有什么安排？
```

复盘时助手应：

- 根据用户反馈更新已完成任务。
- 将未完成但仍有价值的任务保留或标记为推迟。
- 记录用户新增的明日任务。
- 保存复盘记录，包括当天完成内容、未完成内容、明日安排、用户状态备注，以及由复盘导致的任务变更。
- 对没有回应的白天提醒进行轻量追问，例如询问是没看到、在忙，还是不想做。

复盘记录应作为独立数据，而不只是聊天记录。未来助手可以基于复盘历史识别规律，例如哪些时间段经常失约、哪些任务类型容易拖延、哪些提醒风格更有效。

## 飞书接入

第一版采用简单、适合个人使用的飞书接入方式：

- 创建飞书自建应用。
- 通过应用机器人与用户进行私聊。
- 使用飞书消息事件接收用户输入。
- 使用飞书消息发送能力推送提醒、复盘问题和任务确认。
- 事件订阅启用完整加密回调，使用飞书开放平台提供的 Encrypt Key 和 Verification Token。

第一版优先支持飞书私聊。群聊可以后续扩展，但不是 MVP 的默认入口。

飞书只是第一版通知和交互渠道，不应成为业务逻辑的硬编码依赖。后续可能接入其他渠道，例如微信、Telegram、Slack、邮件、短信、网页或移动端推送。

接入设计原则：

- 对用户来说，所有交互都像是在和一个飞书联系人聊天。
- 不依赖复杂飞书表格或文档作为主数据源。
- SQLite 是任务和复盘的主数据存储。
- 飞书只负责消息入口、提醒出口和用户交互界面。
- 公网 webhook 不接受未通过飞书加密解密与 token 校验的事件。
- 业务层只依赖统一的通知渠道接口，不直接依赖飞书 API、飞书消息结构或飞书卡片按钮格式。

## 技术决策

第一版已确认的技术方向：

- 运行环境：云服务器长期运行，服务器有公网 IP。
- 应用语言：Python。
- Web 框架：FastAPI。
- 开发环境：uv 管理 Python 虚拟环境、依赖和锁文件。
- 部署方式：Docker Compose。
- 数据库：SQLite，数据文件通过 Docker volume 或宿主机目录挂载持久化。
- 数据库访问：SQLAlchemy + Alembic。
- 调度器：APScheduler 内嵌在 FastAPI 进程中。
- LLM：OpenAI API。
- Agent 设计：第一版先实现轻量 agent layer，不直接引入重型多 agent 框架；代码保留 `LLMProvider` 抽象，后续可接 OpenAI Agents SDK、LangGraph、Pydantic AI 或其他框架。
- 飞书安全：启用事件订阅加密回调，校验 Verification Token，使用 Encrypt Key 解密事件内容。
- 通知渠道：第一版实现 FeishuChannel，但业务层面向 NotificationChannel 抽象，便于后续接入其他通知渠道。
- 用户模型：第一版单用户运行，配置中指定允许交互的飞书用户或会话；数据表仍保留 `user_id` 字段。
- 时间策略：业务日程按 Asia/Shanghai 计算，数据库存 UTC 时间。
- 配置管理：使用 `.env` 和 Docker Compose `env_file`，提供 `.env.example`，真实密钥不提交。
- 日志：结构化日志输出到 stdout，通过 Docker logs 查看，并对密钥脱敏。
- 测试策略：覆盖核心服务、调度逻辑、webhook 基础处理和持久化，不在第一版做完整飞书线上自动化集成测试。

第一版建议分层：

- Feishu Adapter：飞书事件接收和消息发送。
- Notification Channel：渠道无关的通知发送、按钮动作和用户输入抽象。
- Scheduler：定时提醒、重复提醒、随机提前提醒。
- Task Service：任务解析、增删改查、状态更新。
- Review Service：晚间复盘发起、解析和记录。
- Agent Layer：调用 LLM 理解用户输入并生成回复。
- Storage：SQLite 持久化任务、提醒、复盘和必要上下文。

## 语气和智能感

提醒语言应支持风格调整。第一版默认使用鼓励、轻松、略俏皮的风格，但不能过度打扰或说教。

助手应根据上下文生成消息，而不是只发送固定模板：

- 如果是工作提醒，应结合今日任务。
- 如果是休息提醒，应明确告诉用户可以休息，不继续追问工作。
- 如果是睡觉提醒，应降低刺激感，帮助用户收尾。
- 如果用户反馈不想做事，可以给出理解和轻量建议，而不是强硬催促。

示例：

```text
差不多该切到工作模式了。今天先从客户报价开始，不用完美，先打开文件。
```

```text
午休时间到了。现在不用解释进度，先吃饭和休息。
```

```text
准备收尾啦。今天不用再硬撑，简单复盘一下就可以关机。
```

## 成功标准

第一版成功的判断标准：

- 用户能通过飞书私聊完成任务添加、确认、推迟、取消和复盘。
- 助手能按默认日程主动提醒工作、休息、复盘和睡觉。
- 提醒能提前 10-30 分钟随机触发。
- 未确认提醒能按规则重复，并在达到上限后停止。
- 休息和晚间免打扰规则生效。
- 晚间复盘能更新任务列表，并能生成或保留明日任务。
- 晚间复盘会被保存为结构化记录。
- 任务、提醒和复盘数据会持久化到 SQLite。
- 整体体验不像机械闹钟，而像一个知道当前安排的个人助手。

## 待决问题

- 是否需要区分工作日和周末日程。
- 是否需要支持临时“今天全天免打扰”或“今天状态很差，降低目标”的模式。
- 提醒语气的可选风格有哪些：温柔、严格、俏皮、极简等。
- Docker 部署时 SQLite 数据目录和备份策略的具体服务器路径。
